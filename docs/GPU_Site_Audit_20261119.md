| H09 | 대표 상품 교체 | 대표가격으로 선정된 상품의 교체 이벤트·전후 상품 표시 없음 |

| H11 | 공백 | 보간하지 않는 구현은 확인. Spring 응답 `gaps=[]` 고정이므로 공백 구간·수집 실패/미실시 이유 표현은 미완성 |

## 6. 원가·전기료·IRR·수요·예측

### 원가

현재 계산은 `v02-calculations.js`의 브라우저 함수다. 상태별 원가 항목, USD/KRW 비용 입력, CRF, 매출 마진/가산율, 불완전 원가 경고는 있다. 그러나 아래 차이가 있다.

| 번호 | 요구사항 | 현재 | 필요한 수정 |
|---|---|---|---|
| C01 | 잔존가치 현재가치 차감 | 원가 함수는 `취득비×CRF+운영비` | `(A−S/(1+r)^n)×CRF+운영비` 적용 |
| C02 | 자본비용률 명시·필수 | ‘조달 금리’, 미입력 시 0% 가정 | 차입금리·공개금리·자본비용률 구분, 누락은 계산 거부 |
| C03 | 잔존가치 입력 | 원가 화면에는 없음 | 0도 명시 입력, 0≤S≤투자금 검증 |
| C04 | 취득비 미입력 차단 | 운영비만 입력해도 capex=0으로 계산 가능 | 핵심 투자비 누락과 선택 운영비 미반영을 구분 |
| C05 | 자본비용률 0~100% | 100% 상한 검사 없음 | 필드·서버 공통 검증 |
| C06 | 매출 기준 마진 0~100% 미만 | 음수 매출 마진도 경고 후 계산 | 최신 상세/요구사항 기준이면 거부. API의 구형 규칙도 함께 수정 |
| C07 | 전기단가·IT kW·PUE·시간·환율 | 활성 원가 폼에 없음 | 전기료 필수 계산 블록 추가, 운영비 포함 여부로 중복 차단 |
| C08 | 월별 실제 달력 시간 | 고정 연 8,760시간 계산만 있음 | 월 분석이 필요하면 연·월 및 실제 월시간을 구분. 정규화 730시간과 혼용 금지 |
| C09 | 경쟁사별 후보가격 비교 | ‘동일 조건 표본 없음/연결 필요’ 문구 | 같은 비교 집단의 가격·차액·차이율·마진 연결 |
| C10 | 모델·구성 일치 | 원가 입력은 GPU 수 위주, 시장 필터 전달 없음 | 모델·시스템·상품조건·기간·환율 출처를 분석 컨텍스트에 포함 |

검산 예시(모두 가상 입력): A=400,000 USD, S=100,000 USD, r=5%, n=5년, 운영비=34,000 USD/년, GPU 8개, 가동률70%. 현재 원가식은 **2.576442 USD/GPU·h**, 상세명세의 잔존가치 반영식은 **2.207527 USD/GPU·h**다. 잔존가치를 적용하지 않아 약 16.71% 높다. 이는 이 입력의 계산 차이이며 실제 사업 원가가 아니다.

### IRR와 판매가 추천

| 번호 | 항목 | 현재 | 필요한 수정 |
|---|---|---|---|
| I01 | 기본 IRR | 동작. 초기 유출·연간 유입−현금 운영비·말기 잔존가치 | 공통 서버 모듈과 독립 정답 검산으로 이전/검증 |
| I02 | 목표 IRR 가격 | 단일 최소가격 계산 | 명세의 판매가 추천 범위·후보별 충족 여부와 구분 |
| I03 | 판매가 미입력 탐색 | 판매가격 입력 필수 | 목표 IRR 추천만 요청할 때 사전 판매가 입력 없이 산출 가능하게 분리 |
| I04 | 시장/예측 연계 | 고정 ‘시장 상한 검증 미완료’ 안내 | 실제 조회 결과와 조건부 판정으로 교체 |

| I06 | 민감도 | 없음 | 가격·가동률 변화에 따른 IRR과 조건 미충족 사유 |
| I07 | 원가→IRR 전달 | 최초 일부 자동 입력. 기존 irrInput 우선 | 전달 전 변경 항목 안내, 잔존가치 포함, 직접수정/전달값 출처, 목표 IRR 유지 |
| I08 | 입력 변경 | 기존 결과가 그대로 남음 | dirty 상태와 재계산 안내, 오래된 결과의 후속 전달 차단 |
| I09 | 잔존가치 상한 | 투자금 초과도 계산 허용 | DR-16 기준 상한 검증 |

실제 UI 검산: 투자금400,000, 5년, 운영비34,000, GPU8, 가동률70%, 잔존0, 목표12%, 판매가2.96 입력 → IRR **12.09%**. 함수 결과는 12.087949%, 목표 충족 최소가격 2.955069569였다. 이후 입력 판매가만1로 바꾸면 화면에 이전12.09%가 그대로 남아 입력-결과 혼동을 재현했다.

### 미래가격·수요

- **몬테카를로:** 최종 화면/등록 API에서 12개월 미래가격 실행 기능을 확인하지 못했다. 과거 산점도는 예측이 아니다. 모델·사업자·상품구성·리전·계약·기준일, 표본기간, 중앙값·예측구간·상승/하락 가능성, 반복횟수·시드·모델버전, 데이터 부족 사유, 시간순 검증·기준모델 비교가 필요하다.
- **시나리오 수요:** 사용자 가동률 입력 하나는 존재하지만 시나리오별 유료 판매 GPU시간·매출·IRR을 비교하지 않는다. 요구사항의 보수·기준·낙관 30/50/70% 같은 검증 시나리오를 함께 계산해야 한다.
- **실측 수요:** 상세 FR-74~79는 실제 유료 판매GPU시간/가용GPU시간, 근거·기간, 실측/추정/가정 구분까지 요구한다. 현재 기능은 없다. 다만 최근 요구사항·아키텍처의 사용자 가정 중심 범위와 충돌하므로 필수 범위를 먼저 통일한다.
- **가정 탄력도:** 상세 DR-19의 P0·U0·e 기반 가격별 가동률 가정 모델도 현재 연결되지 않았다. 실측 모델로 표현해서는 안 된다.
- **연계:** 예측/수요 조건이 바뀐 결과의 무효화, 상품·기간·단위 일치 검증, 12개월 예측을 5년 현금흐름으로 자동 연장하지 않는 규칙이 필요하다.

## 7. Spring API 17개 대조

현재 소스의 컨트롤러 등록 기준 **6개 경로 존재, 11개 경로 없음**이다. ‘6개 존재’는 완성도나 테스트 통과율이 아니다. 기존 문서의 4개 구현 표기는 이력·관측 상세 추가 전 기록이므로 그대로 인용하면 틀린다.

| 번호 | 메서드·경로 (`/api/v1` 이하) | 현재 | 프론트 실제 연결/차이 |
|---|---|---|---|
| 1 | GET `/catalog` | 존재 | Spring 모델 목록 사용. 지역 displayName은 null; 전체 UI 필터의 단일 기준은 아직 아님 |
| 2 | GET `/market/summaries` | 없음 | `/api/market`와 프론트 집계로 대체 |
| 3 | GET `/market/offers` | 없음 | Python 현재가/계약 API로 대체 |
| 4 | GET `/market/offers/{offerId}` | 없음 | Python 상품 상세, Spring 관측 상세를 혼용 |
| 5 | GET `/market/observations/{observationId}` | 부분 | Spring 상세 연결. USD만 지원, KRW·일부 근거 미제공 |
| 6 | GET `/market/products/{productId}/contracts` | 없음 | `/api/erd/contracts` 사용 |

### 존재하는 API도 보완할 점

1. 가격 이력: 명세는 사업자·지역·구성·서비스·계약·선납·통화·seriesBy·limit/cursor를 정의하나 컨트롤러는 modelId/from/to 외 입력을 거부한다. 프론트 필터가 있어도 서버 계약 완료는 아니다.
2. 가격 이력: 500개 오퍼 초과 시 전체 오류, nextCursor=null. 홈은 2000년부터 모든 모델 이력을 Promise.all로 일괄 조회한다. 한 모델 오류가 전체 홈 로딩 실패로 이어질 구조다. 필요한 모델·기간 단위 조회와 부분 실패 처리가 필요하다. 성능 수치는 측정하지 않았다.
3. 환산 버전: Python 뷰는 최신 normalization을 선택하지만 Spring 이력은 관측당 환산 버전이 정확히 하나일 때만 선택한다. 규칙이 2개 이상이 되는 경우 두 화면 가격 존재 여부가 달라질 수 있다. 현재 데이터에서 다중버전 재현은 하지 않았으며 코드 경로상의 불일치다.
4. 관측 상세: currency=KRW를 거부, price.krw=null. collectionMethod·excerpt를 null로 고정, assumptions는 빈 배열. 실제 저장값 매핑과 불가 사유 필요.
5. 오류: 등록된 공통 응답에는 meta/errors가 있어 기반은 있다. 다만 DB 오류 코드는 `DATA_UNAVAILABLE`로 명세 `DEPENDENCY_UNAVAILABLE`와 다르고, 알 수 없는 이력 파라미터는 명세의400 대신422 경로다. InvalidRequestException의 구체 이유가 사용자 응답에 사라져 수정할 필드를 알기 어렵다.
6. 미구현 경로는 보안 설정으로 거부될 수 있다. 403 응답만 보고 컨트롤러가 구현됐다고 판단하면 안 된다.
7. 예측·수요 전용 실행 API는 API 목록17개에 없다. Agent의 forecast 중첩 응답은 있지만 화면에서 예측을 시작하는 요청·결과·오류 계약과 IRR 연결 계약은 별도로 정의해야 한다.
